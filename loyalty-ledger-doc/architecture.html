Loyalty Ledger: architecture and data flow

Multi-tenant points engine: ingests high-volume events and guarantees that no points are credited twice or lost.

The repository is still in planning. This is a proposal derived from the README; decisions marked ADR still need to be recorded in loyalty-ledger-doc/adr/.

2. Main flow: an order becomes points

  1. Tenant sends the event in
    OrderCompleted { tenantId, eventId, customerId, amount, occurredAt }
  2. Ingestion API validates and publishes
    Idempotency key = tenantId + eventId. Publishes to loyalty.inbound with partition key tenantId:customerId: all events of an account land on the same partition, in order, processed by a single consumer. Responds 202 Accepted.
  3. Rules Engine calculates the points
    Reads active campaigns from the cache (e.g. "2x on electronics until Nov 30, stock 10,000"). Result: EarnPointsRequested { accountId, points: 240, campaignId, sourceEventId }. If the campaign has stock, it decrements atomically.
  4. Ledger Service writes, in a single Postgres transaction modifies
    1) inserts into idempotency_keys (if it already exists, stops here: duplicate ignored); 2) inserts the transaction and the two ledger_entries (debit/credit); 3) inserts the point_lot with expires_at; 4) inserts the row into outbox.
    Nothing is updated: balance is not a column, it is the sum of the entries.
  5. Debezium publishes from the WAL event
    The commit creates a WAL entry; the Debezium connector (logical replication slot) captures the insert into outbox and the Outbox Event Router publishes ledger.transaction-posted with key aggregateId (= accountId). No polling, and in commit order. If the connector restarts before saving its offset, events are republished; consumers deduplicate by transactionId. The outbox can be cleaned periodically (or the insert followed by a delete in the same transaction).
  6. Projections and consumers react out
    The balance projection in Redis is updated; external services (the "you earned 240 points" notification, analytics) consume the same event.

5. Double-entry ledger: example

Each transaction creates entries that sum to zero. A customer's balance is the SUM(amount) of the entries of their account.

TxOperationAccountAmount
t1Earn (order #881)tenant-A:issuance−240
t1tenant-A:customer-42+240
t2Redeem ($10 coupon)tenant-A:customer-42−100
t2tenant-A:redemptions+100
t3Expiration (lot from t1)tenant-A:customer-42−140
t3tenant-A:expired+140
Balance of customer-42 = 240 − 100 − 1400

6. Failure guarantees

Duplicate event

  • Kafka delivers at-least-once; the same message may arrive twice.
  • idempotency_keys with a UNIQUE constraint inside the same transaction as the entry: the second attempt fails on insert and is discarded.

Consumer dies midway

  • The offset is only committed after the Postgres transaction.
  • If it dies before the offset commit, it reprocesses and hits deduplication. If it dies before the database commit, nothing was written.

Broker down

  • The ledger keeps writing; the replication slot holds the WAL until Debezium can publish.
  • Risk: with the connector stopped for too long, the retained WAL fills the disk. Alert on slot lag (pg_replication_slots) and set max_slot_wal_keep_size.
  • There is never a "written to the database but event lost" case (no dual write).

Hot account (concurrency)

  • Partitioning by account serializes that account's writes without locks.
  • The synchronous path (redemption via API) uses optimistic locking on the account version. ADR: compare both approaches.

Debezium vs custom relay (ADR)

  • Debezium: no polling, low latency, guaranteed commit order, industry standard. Cost: Kafka Connect, replication slot, and WAL to operate.
  • Polling relay (SELECT ... FOR UPDATE SKIP LOCKED): Java code only, easy to test. Cost: interval latency, query load, and trickier ordering with multiple instances.
